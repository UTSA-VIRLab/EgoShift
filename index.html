A stated camera turn gives the answer away.

Ask where an object lands after a 90° turn and you have already ruled out some answers. A model can score well from the turn alone and never look at the image. EgoShift computes how much is given away — from the camera geometry, before any model runs — and builds every question to sit on that bound.

The contribution is the construction, not the scores

Nobody can draw the grey bars above for their own benchmark, because nobody computes them. That is what EgoShift adds: a procedure that derives, from the stated action and the camera geometry, the best score reachable without the image, and then requires every cell of the built data to match it. The derivation, an independent checker and the record of which scenes were ever used in development all ship with the benchmark.

It is not a formality. Applied to our own data — already balanced to the conventional standard, equal answers across the set — the test found a predictor that saw only the stated turn scoring 72.3%. Balancing globally says nothing about what happens inside a single action.

That 72.3% build differs from the released one in other ways too, so it is evidence that the test catches what balancing misses, not a controlled measurement of what the construction bought.

Any benchmark whose questions state an action — a turn, a step, a grasp — can compute the same bound and build against it. That procedure is the part meant to outlive these particular models.

Three tasks, one shared geometry

Match an object across two views, say where it lands after a stated turn, and judge whether it is visible, out of view or hidden behind something. Task B is the primary task; A is a positive control and C is supporting.

Difficulty does not grow with the turn

A 120° turn is answered correctly more than twice as often as a 90° one. Accuracy tracks the number of answers the geometry permits, not how far the camera moved: three answers at 90° and 180°, two everywhere else. Those are exactly the two turns where every frontier system sits on the bound.

At 90° and 180°, 94.8% and 89.9% of frontier answers are identical to the same model’s answer with no image at all.

An earlier build of this data was balanced the usual way — equal answers across the set — and a predictor that saw only the stated turn scored 72.3% on it. Balancing globally does not constrain what happens inside a single turn.

Where the bound comes from

Write z = (r, d) for the stated turn, r its size and d its direction. Five sizes and two directions give ten cells. A predictor handed z and nothing else — no image, no scene, no object, no wording — can do no better than naming the commonest answer in each cell. With S(z) the answers the geometry permits and nz the questions in that cell:

C_min  =  (1/N) · Σ_z  ⌈ n_z / |S(z)| ⌉

Two implementations compute S(z) independently — an interval derivation and a dense enumeration — and a build is accepted only when they agree and every cell attains the bound. For the held-out Task-B set that is 504/1,098 = 45.90%, matched in all ten cells.

The bound covers one shortcut: answering from the stated turn with no image. It says nothing about wording, metadata, or a cue some future model finds. We do not claim the questions are free of shortcuts in general.

Run it

Scoring and auditing need no simulator. The core package has no required dependencies.

git clone https://github.com/UTSA-VIRLab/EgoShift.git
cd EgoShift && pip install -e ".[test,full]"
make check

Score predictions, then audit a split against the geometry:

egoshift score --questions sample/questions.jsonl \
               --predictions sample/predictions.jsonl

egoshift audit-taskb --questions taskb_questions.jsonl

If you report results

Report accuracy per stated turn. A system that raises its pooled score while leaving 90° and 180° on the bound has not improved at the thing this benchmark measures. Submissions go through a results issue; held-out answers are withheld, so we score the file.
